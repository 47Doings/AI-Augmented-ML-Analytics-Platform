# AI-Augmented ML Analytics Platform (prototype)

A business signs up, gets its own workspace, loads data, and the platform runs the whole
chain for it: **SQL analysis -> ML model -> AI-written insights -> business report**.
It is not tied to one business problem: a *use case* is a YAML file plus SQL files, and
the platform code never mentions churn or revenue. Two use cases ship with it:

| Use case | Type | Question |
|---|---|---|
| `churn` | classification | Which active customers are most likely to cancel in the next 60 days? |
| `revenue` | regression | How much will each active customer pay in the next 30 days? |

There are two ways to get data in:

1. **The demo business**: a fictional Accra-based mobile data / home broadband company. Its data is synthetic,
   generated by a seeded script (`datagen/`), with deliberate mess and an answer key to check the SQL against.
2. **Your own data**: upload one CSV (one row per customer, loan, order ...), say which column is the outcome and
   which columns to learn from, and the platform runs the same chain on it. See [Use your own data](#use-your-own-data).

Written for the Npontu Technologies take-home. Snwolley integration: see
[Snwolley](#snwolley-agent-api-toolkit).

## Quick start (Windows PowerShell; Mac/Linux is the same without the activate line change)

Needs Python 3.11+ and Docker.

```powershell
# 1. Database (once)
docker run --name pg-npontu -e POSTGRES_PASSWORD=devpass -p 5433:5432 -d postgres:16
# later sessions: docker start pg-npontu

# 2. Python environment (once)
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt

# 3. Settings (once). Edit .env: set POSTGRES_PASSWORD=devpass and APP_SECRET_KEY (32+ random characters)
copy .env.example .env
python -c "import secrets; print(secrets.token_hex(32))"   # paste this as APP_SECRET_KEY

# 4. Check everything is wired
python -m scripts.check_setup

# 5. Run the app
uvicorn api.main:app --reload
```

Open http://127.0.0.1:8000 and create a workspace. Then either:

- **Try the demo business**: pick a use case, **Generate and load data**, or
- **Use my own data**: choose a CSV, **Upload and check**, answer "what do you want to find out?", **Save choices**
  (a ready-made sample file is in `samples/`).

Then **Run analysis**. When it finishes you get the results, the insights panel and an
**Open business report** link (Print -> Save as PDF).

## Run the pieces without the web app

All from the project root, with the database running. `ws_demo` is just a schema name.

```powershell
python -m scripts.generate_data --schema ws_demo --create-schema --load   # synthetic data -> data/generated + database
python -m scripts.run_sql all      --schema ws_demo                        # clean views, data quality, training table, questions, KPIs
python -m scripts.verify_sql       --schema ws_demo                        # proves SQL is right (answer key + leakage test)
python -m scripts.run_ml train     --schema ws_demo                        # baseline vs models, explanations, model card
python -m scripts.run_ml monitor   --schema ws_demo --cutoff 2026-08-31    # drift (PSI) at a later date
python -m scripts.make_report outputs/workspaces/<schema>/churn            # report.html (+ report.pdf if Playwright is installed)
python -m pytest -q                                                        # all tests (about 3 minutes; the database must be running)
```

Add `--use-case revenue` to the SQL, verify and ML scripts for the second use case.
The notebook is `notebooks/01_churn_analysis.ipynb` (`jupyter lab`).

## Use your own data

**The file.** One CSV where each row is one record. UTF-8, comma, semicolon, tab or pipe separated, with a header
row. Up to 10 MB, 200,000 rows and 80 columns; at least 50 rows. Every row must have as many values as the header
(otherwise the file is refused with the row number, rather than silently shifting columns).

**What you choose** (a form, no SQL):

| Choice | Meaning |
|---|---|
| Kind of answer | *Yes / no outcome* (classification) or *an amount* (regression) |
| Column to predict | the outcome. For yes/no you also pick which value counts as "yes" |
| Row id (optional) | repeated ids are flagged as duplicates and only the first row is used |
| Date (optional) | adds a month-by-month view; must be `YYYY-MM-DD` |
| Columns to learn from | numbers and categories. Free text and unique ids are not offered |

**What the platform does with it**

1. `core/upload.py` checks size, encoding and shape, gives every column a safe name (`Monthly Income (GHS)` becomes
   `monthly_income_ghs`), works out what each column is (number, date, category, free text, unique id) and counts
   gaps. The file is loaded as text into `upload_raw` in the workspace's own schema; the original file is not kept.
2. `core/custom_usecase.py` turns your choices into the same thing a developer writes by hand for the demo: a use
   case (target, inputs, models, metrics, KPIs, AI context) **plus generated SQL**: a clean view (typed, trimmed,
   blanks / `N/A` / `-` as missing, spellings merged, duplicates flagged not deleted), about three data-quality
   checks per column (missing, non-numeric, outliers by the IQR rule, spelling variants, duplicate ids), the training
   table, business questions (outcome by category with `RANK`, by quartile with `NTILE`, month on month with
   `LAG`) and KPIs. The browser never sends SQL: it sends column names, which the server accepts only if it created
   them at upload, and one category value, which it accepts only if the profile saw it.
3. The same pipeline then runs (models, importance, model card, insights, report). Nothing after step 2 knows the
   use case came from a form. The insights and the report say the data was *uploaded by the business*, not synthetic.

**Things you must know**

- **Leakage.** A flat file has no "as of" date, so unlike the demo SQL the platform cannot *prove* an input was known
  before the outcome. It does warn: an input that predicts the outcome almost perfectly (a final status, a
  cancellation date) shows up first in the data-quality table as `possible_leakage:<column>`. You still have to
  decide which columns you would really know in advance.
- **Numbers** are recognised only as plain numbers (`1200`, `-3.5`). `1,200`, `12%` or `GHS 100` count as text, so
  a column full of them will not be offered as a number input; clean it in your source first.
- **Drift check** is skipped for uploads (it needs a later export date to compare against); the model is
  split at random, not by date.
- **Privacy.** Only the numbered facts sheet (summary figures, category names, column names) goes to the AI,
  never rows or ids. Category names come from your data, so do not use a column of personal names as a category.

**A sample to try.** `samples/microloans_sample.csv` is a made-up micro-lender (loan applications, outcome
`defaulted`) with blanks, `N/A`, `Yes` / `yes ` / `YES`, repeated loan ids, a typo and one absurd income. It is test
data, regenerated by `python -m scripts.make_sample_csv` (seeded). Try: classification, target `defaulted`,
outcome `yes`, id `loan_id`, date `applied_on`, tick everything else.

## How it fits together

```
browser -> FastAPI (login, workspace, routes) -> Postgres
                                                   platform schema: users, workspaces, runs
                                                   ws_<id> schema per workspace: raw tables -> clean_* views -> training_set
           own data: upload (core/upload.py) -> profile -> raw table -> column choices -> use case + generated SQL
           pipeline (core/pipeline.py), one function, any use case (demo YAML or your own choices):
             clean layer -> data quality -> training table -> SQL business questions -> KPIs
             -> ML (baseline vs models, importance, model card) -> drift check -> AI insights
           writes results.json + insights.json  ->  web page and business report read ONLY these
```

| Folder | What is in it |
|---|---|
| `db/` | `schema.sql` raw tables, `clean_views.sql` cleaning rules, `platform.sql` accounts/runs |
| `datagen/`, `scripts/generate_data.py` | seeded synthetic data with counted, injected mess + answer key (`manifest.json`) |
| `sql/common`, `sql/churn`, `sql/revenue` | data-quality checks, training tables, KPIs, business questions |
| `use_cases/*.yaml` | a use case: target, features, cutoff, models, SQL files, KPIs, AI context |
| `core/` | config, DB, SQL runner, ML pipeline, drift (PSI), orchestrator, report |
| `core/upload.py`, `core/custom_usecase.py` | the business's own CSV: checks, profile, load; column choices -> use case + generated SQL, leakage warning |
| `samples/`, `scripts/make_sample_csv.py` | a made-up CSV to try the upload path, and the script that regenerates it |
| `core/ai/` | facts sheet, prompt, guardrails, template fallback, **Snwolley adapter** |
| `api/` | FastAPI app, auth/security, static web page |
| `tests/` | datagen, SQL/use cases, ML, AI guardrails, report, API + tenant isolation, upload / mapping / generated SQL |

## Add a new use case (no platform code change)

1. Write `sql/<id>/training_table.sql`: one row per entity, features computed only from data on or before
   `{cutoff_date}`, plus the target looking only after it.
2. Copy `use_cases/churn.yaml` to `use_cases/<id>.yaml`; change the target, features, models, KPIs and the
   `ai:` block (reader, goal, glossary, allowed recommendation types, fallback wording).
3. Run it. The loader rejects a bad config with a readable message (unknown model, target used as a feature,
   unsafe SQL path, and so on). `scripts/verify_sql.py --use-case <id>` checks the SQL and the leakage rule.

The revenue use case was added exactly this way: two SQL files and one YAML.

## What the SQL does

Joins across all six tables, aggregation, and these advanced techniques: window functions (`ROW_NUMBER` for
duplicate customers and latest subscription, `LAG` for month-on-month change, `RANK`, running totals), CTEs
(including `AS MATERIALIZED`), conditional aggregation, `FILTER`, date bucketing, and `UNION ALL`. Data-quality
checks (35) run on the raw tables and are compared against the exact counts of problems the generator injected.
Cleaning lives in views, so raw data is never modified.

## ML in one paragraph

Features come only from data up to the cutoff date; the label looks at the window after it, and `verify_sql`
proves no leakage by deleting all post-cutoff data and checking the features do not change. A dummy baseline is
compared with logistic/linear regression and gradient boosting; hyperparameters and the winner are chosen by
cross-validation on the training split only, and the test split is used once, to report. Explanations use
permutation importance with a noise flag and direction. Same seed + same library versions = same results
(versions are in the model card). Drift is PSI (below 0.10 stable, 0.10-0.25 watch, above 0.25 alert) on every
feature and on the score. Full plan: `docs/monitoring_plan.md`.

## Snwolley Agent API Toolkit

The platform calls the Snwolley agent (`POST https://v1.snwolley.ai/v1/chat/completions/assignment`, header
`X-API-Key`, body `{"message": ..., "stream": false}`) from one file, `core/ai/snwolley_adapter.py`. Put the key in
`.env` as `SNWOLLEY_API_KEY` (never in code or git). `SNWOLLEY_BASE_URL` is optional and defaults to the endpoint
above. With no key the platform still runs and shows a clearly labelled **template summary**.

What the AI layer does (and why it is not a chatbot): it turns the *model and analysis outputs* into an executive
summary, findings, recommendations and caveats. It never sees raw data, only a numbered facts sheet computed
from `results.json`. The endpoint takes one text field, so the rules, facts sheet and required JSON shape are
sent together as one message. Every sentence must cite fact ids and every number is checked against the cited
facts; causal wording, links, unknown citations and recommendation types outside the use case's allowed list are
rejected. A failed answer gets one retry with the reasons, then falls back to the template. The page and the
report label which one they are showing.

Operational handling: the API allows 5 requests per minute. On HTTP 429 the adapter waits for `Retry-After`
(up to 60 s) and retries once; HTTP 401, other errors, timeouts and network failures become a short
"AI provider unavailable" reason (the key is never included) and the run continues with the template summary.

## Security notes

No credentials in code (`.env`, ignored by git; secrets are `SecretStr` and never logged). Passwords use scrypt
with a per-user salt; login errors are generic and throttled; sessions are signed JWTs in an HttpOnly,
SameSite=Lax cookie; each workspace is a separate schema chosen by the server from the login token, never by the
client; SQL identifiers are validated and quoted; the page has a strict Content-Security-Policy and escapes
everything it shows; AI output is validated before display. Uploads are size-capped while they stream, must be
UTF-8 and rectangular, are stored only as text in the workspace's schema and are never executed; their column
names are rebuilt by the server (`[a-z][a-z0-9_]*`) and quoted, and a hostile column name or category value cannot
become SQL (tests in `tests/test_upload.py`).

## Assumptions

- Currency is Ghana cedis. "Churned" means the customer's latest subscription is cancelled with an end date in the
  60 days after the cutoff (2026-06-30). The data runs to 2026-09-30.
- The business is a subscription company: one customer can have several subscription rows (plan changes).
- Duplicate customer records, missing values and inconsistent spellings are normal in the source data and are
  fixed in the clean views, not at load time.
- The revenue target is money from successful payments in the 30 days after the cutoff.

## Limitations (said plainly)

- **Synthetic demo data.** For the demo business, results show the machinery works, not what a real business would
  see. The churn pattern is planted by the generator, so the model finding it is expected.
- **Own data: one flat file only.** No joins across several uploaded tables (see "improve" below). No proof against
  leakage, only a warning (above). No drift check, no date-based split. At most 20 distinct values for a yes/no
  target and 50 for an input category. The generated data-quality checks are generic; they do not know your business
  rules (for example that an age of 150 is impossible).
- **Random train/test split**, not by time (stated in the model card). A time split would be stricter.
- **Small test positives**: about 40 churners in the test set, so metrics move on another sample.
- **Single-process app**: runs use FastAPI background tasks and an in-memory login throttle; a real deployment
  needs a job queue and shared throttle storage (see the architecture note). No email verification, password
  reset or CSRF token (SameSite cookies only).
- **AI guardrails check numbers and wording, not meaning.** Number words ("two thirds") are not checked, whole
  numbers 0-10 are allowed without a source, and a true number can still sit in a misleading sentence.
- **PSI on small samples** is noisy; thresholds are common conventions, not tuned.
- **Snwolley rate limit**: 5 requests per minute, so one run uses one or two calls; many workspaces running at once would need a queue.
- Notebook covers the churn case only.

## What I would improve with more time

1. A monitoring table written by each run, plus a Grafana dashboard (PSI per feature, run success, AI accepted / rejected / fallback rates).
2. Replace the background task with a job queue and scheduler; shared throttle storage; CSRF tokens, email verification and password reset.
3. A time-based train/test split, and performance monitoring once real labels mature.
4. A Kafka consumer for one source (payments) to prove the ingestion path; Elasticsearch for ticket text and the AI audit trail.
5. An "Ask about this run" box that sends a user question plus the same facts sheet to the agent (using `chat_id` to continue the conversation).
6. A notebook for the revenue use case, and a per-request token/rate budget for the AI step.
7. Own data: several related tables with a join mapping (the flat file is the simplest thing that works), business rules per column (valid ranges, allowed values), a time-based split and a drift check when the file has a date, and saving a finished mapping as a reusable template.
